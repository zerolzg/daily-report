# 新闻简报 Telegram 推送改用每日生成的封面图，caption 极简化

简报推送此前只发「标题 + 时间 + 链接」纯文本，观感平淡。我们决定：推送时由 `CoverGenerator` 在本地用 Pillow 给按时段命名的底图（`assets/covers/morning|noon|evening.png`，非固定时段的简报复用 noon 底图）绘制当日日期，在内存中按底图原生 1024x1536 分辨率输出渐进式 JPEG（q82，约 200-320KB，宽高比与原图一致，Telegram 服务端不再二次压缩），经新增的 `sendPhoto` 发送；caption 只保留「🔗 查看完整简报」链接——报刊名与日期已由封面视觉承担，不再文字重复。封面生成或字体解析失败一律降级为原纯文本发送，绝不阻断推送主链路；GitHub 推送失败时的无链接兜底分支维持纯文本，以保留「下个周期重试总结」的既有语义。日期字体用仓库自带的 Noto Sans SC（OFL 协议，已子集化到日期所需字形，仅约 9KB，运行时加粗到 Bold 700），不依赖运行机的系统字体。

## Considered Options

- 每日调用文生图 API 生成全新封面：不可控、有成本、增加推送链路故障面。
- 底图不上仓库、部署时单独下载：多一步部署依赖，图与代码版本可能脱节。
- caption 保留完整标题/时间/链接结构：与封面信息大量重复，浪费 1024 字符上限。
- 复用 Hiragino Sans GB 等 macOS 系统字体：Apple 专有字体不可再分发，且运行机需要额外执行字体安装脚本。
- 封面落盘 `data/covers/` 再上传：多一次磁盘 IO 与清理负担，且每次推送只用一次。

## Consequences

- 新增 `pillow` 运行依赖；打包字体只含「数字 + 年月日 + 星期」字形，若日后要在封面上绘制其他文案需重新子集化字体。
- 底图坐标在 `cover.py` 中按 1024×1024 实测硬编码，更换底图构图需同步更新 `_LAYOUTS`。
- 封面只在内存中生成并随推送即弃，本机不留存历史封面。
